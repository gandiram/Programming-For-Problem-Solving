The idea that holds Unit III together

Divide and conquer. A large problem is split into smaller sub-problems, each solved by its own function. This is the top-down design from Unit I, finally expressed in code — and it is why a 500-line program written as twenty functions is easier to write, test and repair than the same 500 lines written as one.

Part A · User-defined Functions

Writing Your Own Functions

You have been calling functions since Unit I — printf, scanf and sqrt are all functions somebody else wrote. Part A is about writing your own: how to define one, how to call it, and how data travels in and back out.

Why Functions Exist

A function is a named block of statements that performs one task and can be called whenever that task is needed. Functions are the C expression of top-down design: solve a big problem by solving several small ones.

1.1

What you gain

Benefit 1
Reusability

Write the code once and call it a hundred times. The area of a circle is calculated in one place, not in twenty.

Benefit 2
Readability

total = area(r) + area(s); says what is happening. Twelve lines of arithmetic do not.

Benefit 3
Easier debugging

A fault is inside one small function, not somewhere in 500 lines. Each function can be tested on its own.

Benefit 4
Easier maintenance

A formula that changes is corrected in a single place, and every caller is fixed at once.

Benefit 5
Division of work

Different people can write different functions at the same time, provided they agree on the prototypes.

Benefit 6
Abstraction

To call sqrt(x) you need not know how a square root is computed. A function hides how and exposes only what.

1.2

Library functions and user-defined functions

Written byThe compiler vendorYou

Examplesprintf, scanf, sqrt, pow, strlenarea, factorial, isPrime
Source codeNot available to youYours to change
main is a function too

int main(void) is an ordinary function that the operating system calls for you. Its return 0; is a return value like any other — which is why every program you have written so far already had one function in it.

Prototypes and Return Types

  
A function prototype tells the compiler a function's name, return type and parameter types before the function is used. It is the promise; the definition is the delivery.


  

    
3.1
Why the compiler needs it

    
C is compiled in one pass from top to bottom. When the compiler meets add(3, 4) it must already know what add is. There are two ways to arrange that:

    

      
Prototype at the top (preferred)

        
int add(int a, int b);  /* prototype */

int main(void) { ... add(3,4) ... }

int add(int a, int b) { return a+b; }

        
main stays at the top where a reader looks first, and the order of the definitions stops mattering.

      
Define before use

        
int add(int a, int b) { return a+b; }

int main(void) { ... add(3,4) ... }

        
Legal, and no prototype is needed — but with many functions the ordering becomes a puzzle, and two functions that call each other cannot both come first.

    

    

      Prototype syntax
      
It is the function header followed by a semicolon. Parameter names are optional in a prototype, so int add(int, int); is equally valid — the compiler only needs the types. Keeping the names is friendlier to whoever reads it.

    

  


  

    
3.2
Return types, and returning nothing

    

    

      
HeaderMeansCalled as

      
        
int square(int n)Takes one int, gives an int backy = square(5);

        
float avg(int a, int b)Takes two ints, gives a float backm = avg(3, 4);

        
void banner(void)Takes nothing, returns nothingbanner();

        
void show(int n)Takes one int, returns nothingshow(7);

      
    

    

    

      Four mistakes worth remembering
      
1. A function can return only one value. To send back two results you need pointers (Unit V).

      
2. return ends the function immediately — statements after it never run.

      
3. void f(void) and void f() differ: the first says "no parameters", the second says "unspecified". Always write void.

      
4. Calling a void function in an expression — x = banner(); — is an error, because there is no value to assign.

Inter-function Communication

  
Functions talk to each other in exactly two directions: arguments go in, and one return value comes back. Understanding that data is copied on the way in explains nearly every surprise beginners meet.

Where a Variable Can Be Seen, and How Long It Lives

Scope of Variables

  
Scope is the region of the program in which a name can be used. Ask it as a question about place: from where in the source code is this variable visible?


  

    
5.1
The three levels of scope

    

      
    

    

    

      
ScopeDeclaredVisibleAlso called

      
        
BlockInside a { } blockFrom the declaration to the closing braceLocal

        
FunctionAt the top of a function bodyAnywhere in that functionLocal

        
FileOutside every functionEvery function in the file, from that point downGlobal

      
    

    

  


  

    
5.2
Shadowing — when the same name means two things

    
If a local variable has the same name as a global one, the local wins inside that function. The global still exists; it is simply hidden, or shadowed.

    

      
shadow.cthe inner name wins

      
1int x = 100;              /* global */23int main(void) {4    int x = 5;            /* local -- shadows the global */5    printf("%d", x);      /* prints 5, not 100 */6    {7        int x = 2;        /* shadows again, inside this block */8        printf("%d", x);  /* prints 2 */9    }10    printf("%d", x);      /* the block's x is gone -- prints 5 */11    return 0;12}

    

    

      Why globals are discouraged
      
A global can be changed by any function, so when its value is wrong you must inspect the whole program to find out who did it. Functions that communicate through parameters and return values can be understood — and tested — one at a time. Use globals only for genuine program-wide constants.

    

  







  
TOPIC 06Hanly & Koffman §6.6

  
Lifetime of Variables

  
Lifetime is how long a variable's memory exists while the program runs. Scope is a question about place; lifetime is a question about time. They are related but not the same.


  

    
6.1
The two lifetimes

    

      
Automatic lifetime

        
Memory is created when the block is entered and destroyed when it is left. Ordinary local variables work this way — which is why a local starts as garbage on every call, with no memory of the last one.

      
Static lifetime

        
Memory is created once, before main starts, and lives until the program ends. Globals and static locals work this way, and are automatically initialised to 0.

    

    

    

      
VariableScope (where visible)Lifetime (how long it lives)Initial value

      
        
Local (auto)Its block onlyWhile the block is executingGarbage

        
Local staticIts block onlyThe whole program0

        
GlobalThe whole fileThe whole program0

        
Formal parameterIts function onlyWhile the function is executingA copy of the argument

      
    

    

    

      The interesting row
      
A static local has small scope but long life. Only its own function can see it, yet it keeps its value between calls. That combination is exactly what a call counter needs — and it is a favourite examination question.

    

  


  

    
6.2
Trace it — auto against static

Both counters are incremented on every call. Watch only one of them remember.

The static variable keeps one address for the whole run; the auto one is rebuilt each call.

Storage Classes — auto, register, static, extern

  
A storage class is a keyword placed before the type that sets a variable's storage location, default value, scope and lifetime. C has four.


  

    
7.1
The four storage classes compared

    

    

      
Storage classStored inDefault valueScopeLifetime

      
        
autoMemory (stack)GarbageBlockWhile the block runs

        
registerCPU register if possible, else memoryGarbageBlockWhile the block runs

        
staticMemory (data segment)0Block, or file for a global staticThe whole program

        
externMemory (data segment)0The whole programThe whole program

      
    

    

  


  

    
7.2
What each one is for

    

      
auto
The default — you never write it

        
auto int x; means exactly the same as int x;. Every local variable you have ever declared was automatic. The keyword exists for completeness and is essentially never used.

      
register
A request, not an order

        
register int i; asks the compiler to keep the variable in a CPU register for speed, typically a loop counter. The compiler may refuse. You cannot take the address of a register variable, so &i is an error. Modern compilers optimise better than this hint, so it is now rare.

      
static
The useful one

        
On a local: keeps its value between calls and is initialised once, to 0. On a global or a function: restricts it to this source file, so other files cannot see it. Both meanings come down to "limited visibility, long life".

      
extern
Declared here, defined elsewhere

        
extern int total; says "a variable named total exists somewhere else in the program — trust me". It declares without defining, so no new memory is created. This is how several source files share one global.

    

    

      static means two different things
      
Applied to a local variable it extends the lifetime. Applied to a global variable or a function it restricts the visibility to one file. One keyword, two jobs — worth stating carefully in an examination answer.

    

    

      Definition versus declaration
      
int total = 50; is a definition — it creates the memory. extern int total; is a declaration — it only names something that exists elsewhere. A program may declare a variable many times but must define it exactly once.

    

  







  
TOPIC 08Forouzan & Gilberg Ch. 4 · Kernighan & Ritchie §2.4

  
Type Qualifiers — const and volatile

  
A type qualifier adds a promise about how a variable will be used. It does not change the variable's type or size — it changes what the compiler will allow and what optimisations it may perform.


  

    
8.1
const — this will not change

    

      
qualifiers.cconst

      
1const float PI = 3.14159;   /* must be initialised here */2const int MAX = 100;34area = PI * r * r;            /* reading is fine */5PI = 3.0;                     /* ERROR: assignment of read-only variable */

    

    

      const versus #define — a standard examination comparison
      
#define PI 3.14 is handled by the preprocessor as text replacement before compiling. It has no type and no memory address, and the compiler never sees the name.

      
const float PI = 3.14; is handled by the compiler. It is a real variable with a type, an address and proper type checking — which makes it the safer modern choice, and it can be inspected in a debugger.

    

  


  

    
8.2
volatile — this may change behind your back

    
volatile warns the compiler that a variable's value can be altered by something outside the visible program — a hardware register, an interrupt, or another thread. The compiler must therefore re-read it from memory every time rather than caching it.

    

      
Without volatile

        
The compiler sees a loop that never changes flag, so it may load the value once and reuse it forever — and the loop never ends even after the hardware sets the flag.

      
With volatile

        
volatile int flag; forces a fresh read on every test, so the change is noticed. This is why it appears constantly in embedded and device-driver code.

    

    

    

      
QualifierPromise to the compilerEffectTypical use

      
        
constThe program will not modify thisAssignment becomes a compile-time errorNamed constants, safe parameters

        
volatileSomething outside the program may modify thisOptimisations that cache the value are disabledHardware registers, interrupt flags

The C Preprocessor

  
The preprocessor is a separate program that runs before the compiler. It obeys only the lines beginning with #, and its entire job is to produce a modified copy of your source text. The compiler then compiles that copy.


  

    
9.1
Where it sits in the build

    

      
    

    

    

      
DirectiveWhat the preprocessor does

      
        
#include <stdio.h>Replaces this line with the entire contents of the header file. Angle brackets search the system directories.

        
#include "myfile.h"The same, but searches your own directory first.

        
#define PI 3.14Replaces every later occurrence of PI with 3.14.

        
#undef PICancels a previous definition.

        
#ifdef / #ifndef / #else / #endifIncludes or removes whole blocks of code before compilation.

      
    

    

    

      No semicolons on directives
      
#define MAX 100; defines MAX as 100; including the semicolon, so if (n < MAX) expands to if (n < 100;) — a syntax error reported on a line that looks perfectly fine. Directives are not statements and never end with a semicolon.

    

  







  
TOPIC 10Forouzan & Gilberg Ch. 4 · Kernighan & Ritchie §4.11

  
Macros and Conditional Compilation

  
A macro is a name that the preprocessor replaces with text. Object-like macros stand for a value; function-like macros take arguments and look like function calls — but they are not functions, and that difference causes real bugs.


  

    
10.1
Function-like macros

    

      
macros.ctext replacement, not a call

      
1#define SQUARE(x) ((x) * (x))2#define MAX(a, b) ((a) > (b) ? (a) : (b))34y = SQUARE(4);        /* becomes  y = ((4) * (4));  -> 16 */5m = MAX(p, q);        /* becomes  m = ((p) > (q) ? (p) : (q)); */

    

    

      Why every parameter needs its own brackets
      
Written carelessly as #define SQUARE(x) x * x, the call SQUARE(2 + 3) expands to 2 + 3 * 2 + 3, which is 11, not 25. The preprocessor substitutes text, so precedence is decided after substitution. Bracket every parameter and the whole replacement.

    

    

    

      
PointFunction-like macroReal function

      
        
Handled byPreprocessor, before compilingCompiler

        
MechanismText substitution at each useOne copy of the code, called at run time

        
SpeedFaster — no call overheadSlightly slower

        
Program sizeGrows with every useConstant

        
Type checkingNoneFull

        
Argument evaluatedPossibly more than onceExactly once

        
DebuggingHard — the debugger sees the expansionStraightforward

      
    

    

    

      The double-evaluation trap
      
SQUARE(i++) expands to ((i++) * (i++)), so i is incremented twice. A real function would increment it once. Never pass an expression with a side effect to a macro.

    

  


  

    
10.2
Conditional compilation

    
These directives decide which lines of code are compiled at all. The excluded lines are removed before compilation, so they cost nothing at run time.

    

      
debug.c#ifdef

      
1#define DEBUG23#ifdef DEBUG4    printf("x = %d, y = %d\n", x, y);   /* compiled only while DEBUG is defined */5#endif

    

    
Delete or comment out line 1 and every tracing statement disappears from the build — no need to hunt through the file deleting printf calls before submitting.

    

      The other common use: header guards
      
#ifndef MYFILE_H / #define MYFILE_H / … / #endif stops a header being included twice in the same compilation, which would otherwise cause "redefinition" errors. Open any real header file and you will find this pattern at the top.

    

  







  
TOPIC 11Hanly & Koffman Ch. 10 · Forouzan & Gilberg Ch. 4

  
Recursive Functions

  
A recursive function calls itself. It works by reducing a problem to a smaller version of the same problem, until the problem becomes so small that the answer is obvious.


  

    
11.1
Every recursion needs exactly two parts

    

      
Part 1
Base case

        
The smallest problem, answered without calling itself. This is what stops the recursion. factorial(1) = 1.

      
Part 2
Recursive case

        
Solves the problem in terms of a smaller one, and must move towards the base case. factorial(n) = n × factorial(n−1).

    

    

      Miss the base case and the program dies
      
Every call uses memory on the call stack. Without a base case the calls never stop, the stack fills up, and the program crashes with a stack overflow. The runner on this page catches it and says so rather than freezing.

      
The recursive case must also genuinely shrink the problem. return n * fact(n); has a base case but never reaches it.

    

  


  

    
11.2
Trace it — factorial, and the call stack

    
The calls go down until the base case is reached, and then the answers come back up. Nothing is multiplied on the way down.


    

      
Trace — factorial(4) call by call

      
Watch four copies of n exist at once, each in its own stack frame at its own address.

      

        

          
recfact.cexecuting

          

        

          
Call stack — each frame has its own n

            
Every call gets a fresh n at a new address. That is why recursion works.

          
Screen output

        

      

      
InstructionPress Step to begin.

      

        
        
        
        
        
      

    


    

      Reading a recursion on paper
      
Write the calls going down the page, then fill the answers in going back up:

      
fact(4) = 4 × fact(3)
  fact(3) = 3 × fact(2)
    fact(2) = 2 × fact(1)
      fact(1) = 1  ← base case
    fact(2) = 2 × 1 = 2
  fact(3) = 3 × 2 = 6
fact(4) = 4 × 6 = 24

Recursion versus Iteration

  
Anything you can write with recursion you can write with a loop, and the other way round. The choice is about which one states the problem more clearly, and what it costs.


  

    
12.1
The same problem, both ways

    

      
Recursive factorial

        
long fact(int n)
{
  if (n <= 1) return 1;
  return n * fact(n-1);
}

        
Reads like the mathematical definition. Uses n stack frames.

      
Iterative factorial

        
long fact(int n)
{
  long f = 1; int i;
  for (i = 2; i <= n; i++)
    f *= i;
  return f;
}

        
Uses one frame and a couple of variables, whatever n is.

    

    

    

      
PointRecursionIteration

      
        
Repeats byThe function calling itselfA loop construct

        
Terminates onThe base caseThe loop condition becoming false

        
MemoryA new stack frame per call — grows with nConstant

        
SpeedSlower — every call has overheadFaster

        
Code sizeUsually shorter and closer to the definitionUsually longer but more explicit

        
RiskStack overflow if the base case is missedAn infinite loop, but no crash

        
Best forTrees, towers of Hanoi, divide-and-conquer, naturally recursive definitionsCounting, accumulating, straightforward repetition

      
    

    

    

      A practical rule
      
If the problem is defined recursively — factorial, Fibonacci, GCD, tree traversal — recursion usually makes the clearest code. If you are simply repeating something a known number of times, use a loop. For anything performance-critical with large n, prefer iteration.

    

    

      Where naive recursion is genuinely bad
      
Recursive Fibonacci recomputes the same values over and over: fib(30) makes over 1.3 million calls, while the loop version needs 30 steps. It is a beautiful piece of code and a poor algorithm — a good illustration that elegance and efficiency are not the same thing.

01Why functionsReusability, readability, easier debugging and maintenance, division of work, and abstraction. main is a function too.

      
02Defining & callingReturn type, name, parameter list, body. Each parameter needs its own type; return ends the function at once.

      
03PrototypesThe header plus a semicolon, placed before any call. Parameter names are optional; the types are not.

      
04Inter-function communicationActual parameters in the call, formal parameters in the definition. Values are copied in; one value is returned.

      
05ScopeWhere a name is visible: block, function or file. A local shadows a global of the same name.

      
06LifetimeHow long the memory exists. Automatic lifetime ends at the closing brace; static lifetime lasts the whole program.

      
07Storage classesauto is the default; register is a speed request; static gives long life or file-only visibility; extern names something defined elsewhere.

      
08Type qualifiersconst makes a variable read-only and type-checked; volatile stops the compiler caching a value that hardware may change.

      
09The preprocessorRuns before the compiler and obeys only the # lines. #include copies a file in; #define replaces text. No semicolons.

      
10MacrosText substitution with no type checking. Bracket every parameter and the whole replacement, and never pass a side effect.

      
11RecursionA function calling itself, with a base case that stops it and a recursive case that shrinks the problem. Each call gets its own stack frame.

      
12Recursion vs iterationRecursion is clearer for recursively defined problems; iteration uses constant memory and is faster. Both can solve anything the other can.
